# Agent 执行循环、任务预算与 TUI 改进设计

日期：2026-10-09。阶段：多轮 QA 已确认方向，本文供实施前审阅；尚未改动功能代码。

## 1. 目标与已确认选择

解决示例对话中的提前预算中断、工具失败后频繁等待、证据不清楚和 TUI 可读性问题。

| 部分 | 用户确认的方向 |
| --- | --- |
| 执行 | 已授权范围内自动多步执行，普通工具失败后由模型调整方法 |
| 工具等待 | 未返回保持执行中；每次调用有最大等待时间，超时明确返回模型，禁止无限阻塞 |
| 正常结束 | 模型输出独立 XML 标记 `<task_complete/>`，运行器识别后结束 |
| Prompt | 参考本机 AstrBot：一个可编辑主提示词，按需补充能力说明与任务上下文 |
| 结果 | 小结果直接交给模型；大结果返回摘要、关键证据和文件入口，支持按需读取 |
| 预算 | 每任务独立计账，软提示与可配置硬上限；暂停后追加预算继续 |
| 新任务 | 普通消息继续当前任务，通过“新任务”入口或 `/new` 明确开启新任务 |
| 界面 | 对话与任务侧栏；左侧对话和工具摘要，右侧计划、预算、证据与产物 |
| 验证 | 少量关键行为验证和人工对话验证，避免大量测试固化模型决策 |

不增加细分场景 Prompt 路由、多 Agent 平台或新的编排框架。继续沿用现有 LangGraph、工具注册表、模型适配和 Python/Node TUI 桥接。

## 2. 当前代码中的具体问题

- `core/orchestration/decisions.py`：模型没有工具调用时直接进入 clarification 暂停；完成依赖 `finish_task` 及证据校验，不符合本次选择的 XML 结束方式。
- `core/orchestration/execution.py`：普通失败在 `_evaluate` 中立即暂停；`tool_end` 事件只有名称、成功与耗时，缺少可展示结果。
- `core/orchestration/graph.py`、`store.py`：用量日志按会话累计，`submit()` 又可能自动生成新 `task_id`，任务身份和预算边界不一致。
- `efficiency/budget_guard.py`：60%/80% 除提示外还限制工具级别，容易在硬上限之前阻断已授权的任务。
- `core/orchestration/support.py`：完整结果 JSON 进入每轮上下文；已有 `core/context.py`/`efficiency/context_trimmer.py` 未接入这条会话路径。
- `cli/session.py`：固定 Prompt 要求错误后等待，并要求 `finish_task`；`cli/pi_session.py`、`cli/pi/view.mjs` 缺少完整预算、结果与产物状态。
- `tools/registry.py`：统一出口直接等待 `tool.run()`，缺少覆盖所有工具的调用总时限。自定义工具和 MCP 已有局部超时，但取消/子进程回收也可能继续等待，不能当作统一的非阻塞保证。

现有代码已经有循环，改进重点是修正退出、等待、失败和结果注入分支，不重写整个 Agent。

## 3. 执行循环与 XML 结束

正常路径：用户消息 → 模型选择动作 → 校验及必要授权 → 工具执行 → 保存结果 → 精简结果返回模型 → 模型决定下一步。

模型可以调用多轮工具。普通连接失败、工具返回失败或可修正参数错误作为结果返回模型，由模型选择重试、调整或其他方法；失败不自动结束任务，也不直接要求操作员点“继续”。真实缺少输入由 `ask_user` 进入等待。模型不可用、预算硬上限、显式停止和原有恢复歧义各自保留独立暂停原因。

保留代码层目标范围和授权门控。已有 L1 授权在其覆盖范围内继续有效；L2 解锁和逐动作确认维持现有规则。预算软提示不撤销授权，自动继续也不替代授权。执行已开始但结果未提交的恢复记录继续要求明确 retry/skip，防止自动重复副作用。

唯一正常完成协议：模型先写结论，再在助手正文最后单独输出一行：

```xml
<task_complete/>
```

运行器在完整回复收到后识别该行并设为 completed，展示时去除标记。标记不能从工具结果、用户消息、reasoning 内容或代码块内提取；只匹配独立正文行。如果回复同时含工具调用，先处理工具调用，本轮标记不触发完成，模型需在后续无待执行调用的回复中结束。

无工具调用、无结束标记的普通回复继续进入模型决策，并补充简短协议提醒，不能仅因这一情况暂停。保留现有可配置决策/动作段上限作为异常循环的暂停保护，不增加新的“完成审判”或额外 LLM 审核步骤。

不再向模型暴露 `finish_task` 作为完成要求，保留 `update_plan` 和 `ask_user`。已保存历史中的旧控制调用可读取，不把历史调用重新执行。任务完成由模型判断，不再要求“必须有一次成功工具调用”才能结束普通问答。

预算、错误或用户停止导致的中断不生成结束标记，不显示 completed；已有结果可以生成带未完成状态的报告。

### 3.1 工具执行状态与最大等待时间

工具执行的状态与最终结果分开记录：授权完成并真正启动后为 running；正常返回才结算成功/部分成功，明确异常才结算 failure，到达调用截止时间才结算 timeout。没有新输出、没有 stdout 或尚未收到返回值，都不是失败依据。运行记录至少包含 execution_id、开始时间、已用时间及实际等待上限。

等待期间由运行器的独立计时/状态事件更新 TUI，例如“等待工具返回，已用 45s / 上限 120s”，有真实进度时再展示进度。存活的任务和心跳只能证明调用尚未结算，不能声称工具持续取得进展；无法判断是否卡住时明确保持等待，最终由截止时间结束等待。此期间不反复调用模型来猜测工具是否失败。

每次调用使用正数、可配置的最大等待时间，建议全局默认 120 秒；已有工具明确配置的时限优先，并允许逐工具覆盖。实际采用的时限在启动事件中展示。计时使用单调时钟，从实际执行开始，覆盖连接、重试和函数整体等待；重试或收到输出不能重新开始计时。授权等待不计入工具执行时限。HTTP/MCP/子进程的内部时限仍保留，适配器内部各阶段共享剩余调用时间，不能通过嵌套超时无限延长总等待。

到达上限时，运行器停止等待该调用，发起取消并执行有界清理（建议最多额外 5 秒），保存已捕获的输出和诊断。向模型交付一次明确的超时结果：`status=timeout`、`success=false`、`error_code=TOOL_TIMEOUT`，附工具名、execution_id、等待上限、实际耗时、部分证据/产物入口及取消状态。摘要明确说明“工具超过最大等待时间，未取得完整结果”，不把超时解释成目标服务不存在或执行已经失败。若是工具内部某个端口连接超时、但整个函数已正常返回，应作为观察或部分成功处理，不能误标为整个调用超时。

取消与实际停止必须区分：可取消的异步 I/O 取消请求；本地命令/脚本终止并回收本次调用拥有的进程及子进程；会阻塞事件循环的同步函数必须在可终止的独立工作进程执行。不能仅用 `asyncio.wait_for` 或移到普通线程就声称可以强制结束任意函数；取消协程本身也可能等待，清理不能再次无限阻塞主事件循环。

远端 HTTP/MCP 动作或未确认停止的外部执行，结果标记 `outcome_unknown=true` 并说明可能仍在执行。模型可以根据超时选择其他安全方法；存在副作用且状态不确定的同一动作禁止自动重试，沿用明确恢复/确认流程。无法完成的清理保留执行记录，由独立回收路径继续跟踪；TUI 输入、停止、新任务及其他状态操作必须仍可响应。

超时结算以 execution_id 保证只交付一次工具回复。截止后迟到的返回只能追加为迟到诊断/证据记录，不能覆盖已交付的 timeout、再次触发同一调用的模型决策，或把新任务状态改成旧调用成功。实际未停止的调用即使进入新任务也保留其记录及重复执行限制。

## 4. 主提示词与能力注入

提供一个默认主提示词，允许本地配置文件覆盖。主提示词表达任务推进、失败/超时后调整、证据引用、未知项说明、按需读取产物和 XML 完成协议；不按 Web/SSH 等细分场景建立不同工作流。明确告知模型：未收到工具结果时属于等待；收到 TOOL_TIMEOUT 才代表调用等待超时，外部执行状态不确定时不能假定已停止或自动重复动作。

沿用渐进披露：默认提供工具目录/简介，选定能力后加入必要说明与 Schema。追加当前任务目标、授权状态、计划、预算状态和证据索引。Prompt 的描述不能覆盖实际工具范围及授权校验。

提示模型在重要动作前简述目的，工具返回后解释依据和下一步；不要求每次工具调用都长篇输出，也不要求展示模型内部思维链。

## 5. 工具结果、证据与产物

沿用 `ToolResult` 和现有 `EvidenceStore`，增量扩展，不让已接入的内置、自定义命令/脚本/HTTP、MCP 和 JS/API 工具分别实现不同协议。

结果提供以下语义：

- `status`：成功、部分成功、失败、超时、取消；兼容现有 `success`。running 属于执行状态事件，不能提前生成失败结果。
- `summary`：可供模型和界面使用的简要结果。
- `evidence`：兼容现有来源列表；结构化观察可保存在 `data` 中并关联真实证据 ID、执行 ID、来源、目标及范围。
- `artifacts`：真实保存的文件入口、类型、大小、用途及内容哈希（已有哈希机制可复用）。
- `error`：具体失败/超时原因与错误类别；同时保留已有 stdout、stderr、exit_code 等诊断数据。超时额外携带等待上限、耗时、取消状态及外部执行是否不确定。

“443 连接超时”是观察，不能自动变成“目标没有 Web 服务”。异常/失败也保存实际诊断信息，但不能把错误日志或模型推断标成已验证发现。无文件则不生成虚构路径；产物保存失败须在返回结果中说明。

小结果保留关键结构和内容直接返回。超过可配置大小阈值时保存完整结果，模型收到摘要、关键观察、错误、文件或证据入口及可用读取方式；不把所有原始输出再次拼进上下文。摘要优先采用工具已有结构，通用摘要可用确定性字段提取，不为每次工具执行额外调用模型。

复用/扩展 `evidence_read` 提供分页或分块读取。模型读文件的结果同样受大小阈值约束，避免一次读取又塞回整个大文件。保留现有证据对象的大小及完整性限制；超过单对象上限的数据使用受控分块或独立产物文件，不能静默截断后声称已保存完整内容。

TUI 默认展示动作目的、状态、摘要、证据入口，参数、原始输出和详细错误展开查看。此展示默认沿用前面讨论的摘要方向，最终可在界面验收时调整。

## 6. 上下文与预算

区分两种量：一次请求的上下文长度，以及任务已经累计花费的输入/输出 tokens 与已知费用。上下文压缩只减少后续请求长度，不减少已花费用量。

优先复用现有 ContextTrimmer。精简长工具结果与旧历史，保留主提示词、当前目标、授权提示、计划、关键证据入口、未知项和最近用户指令。原始对话与工具记录留在会话存储；不能破坏原生 tool call/reply 对应顺序或遗漏未完成调用。压缩无额外模型调用作为默认实现。

任务日志按 `session_id + task_id` 保存累计用量和预算上限，会话另保留总用量。普通消息和恢复保持 task_id；上下文压缩、模型重试、断线恢复和追加预算都不能重置已用量。服务商返回的 usage 优先；缺失时使用明确标为估算的用量，保留已知费用与费用未知状态，避免前后层重复计账。

默认沿用现有 60,000 tokens / USD 2 的硬上限与可配置项。60%/80% 作为软提示，不再按工具级别自动阻断动作；每次模型调用前检查硬上限。单次请求实际消耗仍可能跨过上限，下一轮暂停并准确记录超出量。达到任一已知硬上限后保存当前任务、计划、证据、产物及未完成项，不再调用模型来补一份结束总结。

提供追加预算入口：增加当前任务的 tokens 或费用上限，不清零已用量；两种上限都满足后恢复同一任务。CLI 和 TUI 使用同一运行器操作。暂停界面说明限制维度和追加后的继续方式。

旧会话只有会话累计用量时，将已有累计量绑定到恢复的当前任务，并保留会话累计量；执行 `/new` 后才创建独立的新任务预算，避免升级时抹去已有消耗。

## 7. 明确的新任务边界

`/new` 与 TUI“新任务”入口调用同一操作：保存旧任务，创建新 task_id，使用默认任务预算、空计划及当前任务结果索引；旧任务历史和产物仍保留在会话存储。新任务只注入主提示词、当前工具配置和目标/授权上下文，不自动带入旧任务的长对话。相同工具签名的旧任务完成记录不能被当成新任务已经执行。

若任务运行中，先取消并等待本轮保存完成，再创建新任务；不在旧动作仍运行时直接清空计账或覆盖检查点。旧执行状态不确定的记录仍保留为不确定，不伪装成功。`/new` 不发起扫描，也不自动调用模型。

普通消息包括完成后的追问都属于当前任务；只有明确的新任务操作重新计账。无需模型判断用户是否换了话题。工具设置保留，授权沿用当前进程已有门控状态；进程重启的授权恢复继续遵守原规则。

## 8. 对话与任务侧栏 TUI

采用用户选中的示意布局：左侧对话流、工具摘要和输入框，右侧显示当前计划、预算和证据/产物索引。宽度不足时折叠侧栏，可通过键盘切换查看，不能压缩对话到不可读。

状态显示中文：运行中、等待输入、等待授权、预算暂停、异常暂停、已停止、已完成。等待显示原因及可执行操作，不用统一 paused 混淆不同原因。预算显示本任务已用/上限/余量及估算标识，会话总量为次要信息。

主题采用示意中的克制青绿强调色，提供适合暗色/浅色终端的配色，兼容 NO_COLOR。使用现有 Pi 组件和布局接口，保留键盘交互。主题只改变展示，不承担授权或预算判断。

桥接事件扩展工具摘要、结果状态、证据与产物、任务预算和暂停原因，以及工具开始时间、已用时间、等待上限与清理状态。没有结果时显示“等待工具返回”；deadline 到达后显示“工具超时”，不让前端依据无输出自行推断失败或完成。流式内容只作为预览，完整回复解析后才正式显示任务完成；XML 控制标记不进入可见对话。

## 9. 改动边界与验收

先落实执行协议和失败返回，再统一结果/产物与上下文，然后修正任务预算、新任务边界及恢复，最后完成状态桥接和侧栏主题。报告同步标注 task_id、任务与会话用量、证据/产物以及未完成状态，保留既有导出格式。

只修改服务于本次任务生命周期的模块；现有工具接入和 auth 可选配置继续兼容。默认工具结果适配在公共出口完成，再逐步丰富内置工具已有结构，不要求同时重写每个工具。

验证保持精简，以少量协议/运行器场景和人工验收为主，不给每个 Prompt、场景或模型措辞建立测试。关键场景：

1. 工具成功或普通失败后，结果进入下一轮，模型能继续调用并最终以 XML 结束；普通问答也可直接以 XML 结束。
2. 工具输出或代码块中的标记不会误结束；未授权动作仍需真实授权。
3. 大输出真实落盘，模型收到关键摘要，可按需读回，文件不虚构。
4. 预算软提示不提前阻断；硬上限暂停，追加后继续且用量不重置；`/new` 开新任务预算，会话总量保留。
5. TUI 展示对话、计划、预算、证据与产物，宽窄终端都可用，控制标记不可见。
6. 长工具无输出但仍在等待时不误报失败；截止后一次性返回 TOOL_TIMEOUT 给模型，主事件循环及输入仍响应，迟到结果不重复结算。使用可控制的模拟慢工具覆盖正常慢返回、超过时限及状态不确定三个边界，不增加真实长时间探测测试。

尽量调整已有相关测试，新增只覆盖无法由现有测试验证的关键边界。人工示例使用模拟工具/模型或本地数据，不因为设计验证自动向示例 IP 发起探测。
